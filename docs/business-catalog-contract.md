# Business catalog contract
Taxonomy: exact selectable labels in assets/js/business-model.js exports SKILLS and INTERESTS. A selected parent does not imply a selected child. 15 skill roots and 14 interest roots, each three branches with three leaves. Selection limit: 10 labels per side.
Catalog: content/business/<domain>.json arrays. Each record: {id,title,service,customer,skills:[exact skill labels],interests:[exact interest labels],allInterests?:[[exact labels]],family,needs,first,ratings:{startup:'Low'|'Moderate'|'High',learning:'Short'|'Practiced'|'Deep',growth:'Solo'|'Team'|'Scalable'}}.
skills and interests are separate OR eligibility gates (at least one exact selected label from each). allInterests adds AND-of-OR clauses that must each match an actually selected interest. Dogs + Walking or Walking dogs must be explicit for dog walking. Never treat parent Animals or Outdoors as dog walking intent. Broad roots are okay for ordinary non-specialist services only when they truthfully imply aptitude/interest. No regulated professional claims.
Each idea must be a distinct concrete deliverable/customer/problem; avoid trivial niche renames. Concise service and customer, practical needs and specific tiny first-customer action. Ratings are editorial guidance, not forecasts. Low startup = ordinary basic tools; Moderate = equipment/logistics; High = substantial equipment/permissions. Short learning = narrow repeatable task; Practiced = portfolio/consistent competence; Deep = sustained specialist mastery. Solo = primarily personal time; Team = repeatable service/team; Scalable = reusable digital or physical product/licensing.

## Matching and maintenance

`business-model.js` retains the exact taxonomy; `docs/business-taxonomy.json` is its inspectable snapshot. Match only literal selected labels. Separate skill and interest OR gates must both pass; each `allInterests` OR group must also pass. A reported passion never becomes an aptitude. Eligibility is filtered before ranking. No subject aptitude, budget, time, equipment, location or willingness is inferred; these are not questionnaire fields.

Eligible scores use the most specific reported matching skill (root1, branch2, leaf3) ×4 and interest ×3, plus at most3 matched labels per side. Stable ID order resolves ties independently of questionnaire click order. Prefer an unused daily-work family within4 points of the best remaining eligible score. Diversity never admits an ineligible idea. Return at most3; zero/one/two matches are shown honestly with a refinement action. Explanations contain only actual matching answers. The same module runs in browser and Worker; server submissions derive their own current recommendations.

The catalog is an editorial library, not a researched ranking, earnings forecast or statement of professional qualification. Startup measures setup effort/tool/logistics burden; learning measures the practice required for dependable work; growth describes personal delivery, repeatable team delivery or reusable products. Needs state practical prerequisites; first steps start with a narrow sample or pilot.

Edit the relevant JSON file, preserve stable IDs for the same offer, and use new IDs for materially different offers. Check actual deliverable/problem/production skill for duplication; unique titles alone are insufficient. Share family names for related daily work across domains. Add exact gate labels only when actual production work and topic fit; never broaden them to fill a count. Keep specialized claims gated to the corresponding skill. Every walking offer must retain both explicit dog and walking interest clauses.

Run `node scripts/build_business_catalog.mjs`, `node --test tests/test_business_catalog.mjs`, backend `npm test`/`npm run check`, and relevant browser tests. The build checks count500, valid labels, IDs, normalized titles/offers, ratings and card length. Exhaustive single-answer coverage in `outputs/business-catalog/coverage.json` is descriptive: many cross-domain pairs legitimately have no strong match. Review gaps editorially rather than weakening gates. The All choices dialog permits exact leaf selections directly. Never claim every pair yields three.

For a release, begin with the verified current production snapshot and overlay only the owned feature assets plus the matching bundle change. Compare unrelated asset and embedded-source hashes, retain bindings/routes/config, review independently, and record before/after production version and HTTP receipts. Keep source JSON, instructions, tests and QA artifacts out of public assets.
